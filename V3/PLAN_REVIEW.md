# V3 计划评审

## 评审准则

每个阶段按以下两个维度评估：

1. **是否有助于产出短剧？** — 该功能是否直接或间接提升用户创作短剧视频的能力？
2. **是否有助于判断进度或卡点？** — 该功能是否帮助用户了解内容在流水线中的位置，以及什么阻碍了完成？

---

## 逐阶段评审

### 第一阶段：TaskLogger 全量集成

**结论：保留 — 关键级别 (P0)**

- **产出短剧？** 间接有帮助。没有任务历史，用户无法获得反馈。提交解析任务后毫无反应——没有历史记录，没有状态更新。这打断了"上传小说→解析→生成剧本→渲染视频"的核心工作流。
- **判断进度/卡点？** 直接有帮助。任务历史的首要目的就是回答"我的任务发生了什么？"当前缺少 logger 集成，解析和渲染任务完全不可见。用户无法知道小说解析是否成功、提取了多少章节、为何失败。
- **不做的风险**：解析流程（所有短剧创作的入口）始终是一个黑盒。这是用户最初反馈任务 `308e1f07` 消失问题的根因。

---

### 第二阶段：可读标识符

**结论：保留 — 高价值 (P1)**

- **产出短剧？** 间接有帮助。当用户拥有 5 本都叫"测试小说"的小说时，在任务历史或项目分配中无法区分它们。识别错误会导致用错误的章节生成剧本。
- **判断进度/卡点？** 有帮助。任务历史显示"NOV-280428-A3F2 解析失败：编码错误"可立即定位问题。而"6123f450-2188-444f-a847-df95944afe20 解析失败"需要用户手动逐个对照 UUID。
- **不做的风险**：系统仍可使用，但规模扩大后会极度影响效率。UUID 不适合人类识别。

---

### 第三阶段：任务列表重新设计

**结论：保留 — 高价值 (P1)**

- **产出短剧？** 对内容生成质量无直接影响。
- **判断进度/卡点？** 直接且显著。当前任务列表显示原始 Celery UUID，无排序，无状态筛选，耗时以原始毫秒显示。用户无法回答"今天什么失败了？"或"哪个任务最耗时？"这类基本问题。
- **关键改进点**：
  - 时间排序 → "刚刚发生了什么？"
  - 状态筛选 → "只看失败的"
  - 耗时格式化 → "解析通常需要多长时间？"
  - 失败原因列 → "为什么会失败？"（当前隐藏在可展开 JSON 中）
- **不做的风险**：用户手动浏览未排序列表浪费大量时间，流水线问题排查效率低下。

---

### 第四阶段：任务类型分类页面

**结论：保留 — 中等价值 (P2)**

- **产出短剧？** 无直接影响。
- **判断进度/卡点？** 有帮助，面向管理特定流水线阶段的用户。排查"为什么我的剧本没有生成？"时，专属的剧本生成任务视图展示剧本标题、场景数、剧集链接等专属列会非常有帮助。
- **价值论证**：不同类型的任务关注的信息完全不同。解析关注章节数，生成关注场景数，渲染关注分辨率和时长。统一表格要么隐藏类型专属信息，要么变得杂乱。
- **不做的风险**：用户仍可通过第三阶段的类型下拉筛选实现类似效果。专属页面是组织性改进而非能力解锁，可推迟至 V4。

---

### 第五阶段：任务结果富化

**结论：保留 — 中等价值 (P2)**

- **产出短剧？** 无直接影响。
- **判断进度/卡点？** 有帮助。显示"解析小说 — NOV-280428-A3F2 斗破苍穹"远比"解析小说 — args: ('abc123...', '/novels/...')"更有用。关联上下文让用户从失败任务直接跳转到受影响的小说。
- **不做的风险**：第三阶段的"关联对象"列会显示原始 ID 而未经富化。功能上仍可用，但体验不完善。

---

### 第六阶段：失败诊断与恢复

**结论：保留 — 高价值 (P2)**

- **产出短剧？** 间接有帮助。当解析任务因编码失败时，用户当前会看到难以理解的 Python 异常堆栈。有了错误分类，用户看到"文件编码不支持，请上传 UTF-8 编码的文件"并可修复文件后重试。重试按钮闭合了整个恢复循环。
- **判断进度/卡点？** 直接有帮助。核心目的是将不透明的错误转化为可操作的指导。重试按钮消除了返回小说页面重新点击"开始解析"的需要。
- **不做的风险**：用户持续被无法理解的错误信息阻塞。用户的原始诉求（"解析失败"）正是如此——知道失败但不知道为什么、不知道如何修复。

---

### 第七阶段：实时任务进度

**结论：推迟到 V4 — 锦上添花，非必需**

- **产出短剧？** 否。进度条不会产出更好的短剧。
- **判断进度/卡点？** 有限帮助。对于长时间运行的任务（如视频渲染），进度条告诉用户"仍在运行"还是"已卡住"。但当前 NovelDetailPage 中的 3 秒轮询已提供基本的"是否完成"反馈。
- **投入产出分析**：SSE 端点、Redis 发布订阅、前端进度条、每个任务函数中的进度上报——实现工作量很大，但只得到了一个 UX 细节。当前轮询已足够。
- **建议**：在 1-6 阶段部署完成且用户反馈无法判断任务进度时再重新评估。

---

### 第八阶段：解析任务健壮性

**结论：保留 — 关键级别 (P0)**

- **产出短剧？** 直接有助于。解析任务是入口——如果失败，就无法生成剧本，无法渲染视频。增强其健壮性（编码回退、文件校验）可确保流水线可靠启动。
- **判断进度/卡点？** 有助于。API 路由层的前置校验（在入队前检查 MinIO 文件是否存在）提供即时、清晰的反馈，而不是 Celery 任务静默重试 3 次×3 分钟后再消失。
- **不做的风险**：用户报告的 Bug（解析失败、任务在历史中不可见）不会被修复。中文小说普遍使用 gb2312/gbk 编码，对中文短剧平台而言这一点的修复尤为关键。

---

## 汇总

| 阶段 | 结论 | 理由 |
|------|------|------|
| 1: TaskLogger 集成 | **保留** | 关键 Bug 修复 — 缺少则任务不可见 |
| 8: 解析健壮性 | **保留** | 整个流水线入口的关键修复 |
| 2: 可读标识符 | **保留** | 多小说/多项目工作流必备 |
| 3: 任务列表重设计 | **保留** | 核心可观测性 — 排序、筛选、可读列 |
| 6: 失败诊断 | **保留** | 不透明错误→可操作指导 + 重试兜底 |
| 4: 任务分类页面 | **保留** | 类型专属列提高各阶段排查效率 |
| 5: 任务结果富化 | **保留** | 可点击链接闭合排查循环 |
| 7: 实时进度 | **推迟** | 投入产出比低，当前轮询已够用 |

---

## 推荐实施顺序（评审修订版）

```
P0 (立即修复)
├── 第一阶段: TaskLogger 全量集成
└── 第八阶段: 解析任务健壮性

P1 (高优先级)
├── 第二阶段: 可读标识符
└── 第三阶段: 任务列表重设计

P2 (后续完善)
├── 第六阶段: 失败诊断与恢复
├── 第四阶段: 任务分类页面
└── 第五阶段: 任务结果富化

推迟至 V4
└── 第七阶段: 实时任务进度
```

## 最终结论

V3 计划中 7 个阶段（共 8 个）通过评审，确认为必需或高价值功能。**第七阶段（实时任务进度）**被推迟至 V4，理由是当前轮询机制已提供基本的进度反馈，而 SSE + Redis Pub/Sub 方案的投入产出比在当前阶段不合理。

P0 阶段的修复直接响应用户的原始诉求（任务 308e1f07 不可见、解析失败无原因），应作为最高优先级立即实施。
